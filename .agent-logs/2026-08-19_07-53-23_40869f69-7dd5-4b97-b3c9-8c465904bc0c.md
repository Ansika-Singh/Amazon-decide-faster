## 1. Design system to use (already established — do not invent a new one)

- **Display/UI font:** Space Grotesk
- **Monospace/data font:** IBM Plex Mono (use for stats, timestamps, IDs, code, streak counters — anywhere a number or system value appears)
- **Palette:** warm-ink theme — dark ink/charcoal base, warm off-white text, a single warm accent (rust/amber-ink, not Anthropic-clay #D97757, not generic purple/indigo SaaS gradients). Keep the accent to one hue family and use it sparingly: primary actions, active states, streak flame, badges. Everything else is ink, warm grey, and paper-white.
- **Radius/spacing:** consistent scale, sharper corners over bubbly ones — this is a builder/technical platform, not a lifestyle app.
- **Iconography:** one consistent icon set throughout (pick one — Lucide or Phosphor — never mix).

Every new page must derive from this system. If a page you're about to build doesn't obviously belong next to the Phase 1 modules (Hackathon Management, Daily Challenges) already shipped, stop and reconcile the styling before writing markup.

## 2. Global interaction contract (applies to every module, every role)

These rules are non-negotiable and apply everywhere "Add," "Edit," "Delete," "Join," "Apply," or "Submit" appears:

**Add / Create**
- Opens a form (modal or dedicated `/new` route — modal for quick objects like a challenge submission, full page for heavy objects like a hackathon listing or a company profile).
- Form fields must match the actual data model for that content type — a "new hackathon" form asks for title, dates, tracks, prize pool, eligibility, judging criteria; a "new daily challenge" asks for difficulty, topic, time limit, points. No generic "Name / Description" placeholder forms.
- On submit: optimistic UI update, the new item appears in its list/grid immediately with a subtle entrance (fade + 4–8px rise, ~150–200ms, no bounce), plus a toast confirming what was created, in active voice ("Hackathon published" not "Submission successful").
- Validation errors are inline, specific, and appear at the field, not as a generic banner.

**Delete / Remove**
- Never deletes on a single click. Always opens a confirmation dialog naming the specific item ("Delete 'Winter Code Sprint 2026'? This removes all 340 submissions and can't be undone.") — not a generic "Are you sure?"
- Destructive confirm button is styled distinctly (not the accent color — a clear danger state) and requires an explicit second click.
- On confirm: item animates out (fade + collapse, not just vanish), list reflows, toast confirms what was removed with an undo window where the action is safely reversible (e.g., removing a saved job, but not e.g. deleting a live hackathon with submissions).

**Join / Apply / Register**
- Also gated behind a confirmation dialog when the action has consequences (joining a hackathon locks you into a team size, applying to an internship uses one of a limited application count, joining a challenge starts a timer). Dialog states exactly what happens next.
- Once confirmed, the button state changes permanently and visibly (e.g., "Join Hackathon" → "Registered ✓", disabled, with a link to "View my team").

**Edit**
- Inline editing where the object is small (profile fields, a single challenge answer) — full form where the object is complex (hackathon details, company listing).
- Every edit shows a "last updated" timestamp in the mono font.

**Empty states**
- Every list, table, and grid needs a real empty state: a short line of copy in the interface's voice explaining what goes here and a primary action to fill it. Never a blank div. ("No submissions yet. Once your team submits a project, it'll show up here." + a `Submit project` button if the user is the one who should act.)

**Motion**
- Subtle only: 150–250ms ease-out for entrances/exits, hover states that shift opacity/elevation by a small amount, no parallax, no spinning icons, no confetti unless it's a genuine milestone (winning a hackathon, hitting a 30-day streak) — and even then, once, not on every page load.
- Respect `prefers-reduced-motion`.

## 3. The profile & streak system (every role has this — it is the connective tissue of the platform)

This is the one screen every role sees and it should feel like Unstop's profile page crossed with a GitHub contribution graph:

- **Header:** avatar (real upload, with crop-on-upload), name, role badge, headline/tagline, location, and a "Profile strength" meter (like LinkedIn's) that's actually computed from filled fields, not decorative.
- **Streak system:** a visible daily-login/activity streak (current streak count + longest streak, in mono font, with a flame or equivalent accent icon that only lights up warm-accent when the streak is active today). Logic: streak increments once per calendar day on qualifying activity (login alone can count, but weight it lower than "did a challenge / submitted something" — define this clearly in the data model so it can't be gamed by just opening the app).
- **Activity heatmap:** a contribution-graph-style calendar (like GitHub's) showing daily activity density for the last 3–12 months, hoverable per day with what happened that day.
- **Daily log:** a real log of dated entries — challenges completed, hackathons joined, badges earned, applications sent — reverse chronological, each entry links to the actual object.
- **Badges/gamification:** earned badges rendered as a real grid with locked/unlocked states, hover shows criteria for locked ones.
- **Role-specific stat block:** see per-role sections below — this is not the same three stats reused for everyone.

Build this once as a shared component with role-specific slots, not four separate profile pages that drift out of sync.

## 4. Role-based internal experiences

Each role gets its **own dashboard home and its own subset of subpages** — not the same shell with a filtered sidebar. The nav items, the primary actions surfaced, and the data shown should feel like they were designed for that person's actual weekly workflow.

### Student
Dashboard home leads with: active hackathons they're registered for (with countdown), today's daily challenge (if not done, this is the most prominent card on the page), current streak, and applications in progress.
Subpages:
- `/hackathons` → browse/filter → `/hackathons/[id]` (details, rules, timeline, prize, judges) → `/hackathons/[id]/team` (form/join team, invite by email/code) → `/hackathons/[id]/submit` (submission form: repo link, demo link, description, track selection)
- `/challenges` → daily challenge archive with streak calendar, `/challenges/[id]` solve view with the AI Evaluation module giving live/instant feedback and a score breakdown (not just "8/10" — show what the AI evaluated: correctness, code quality, approach)
- `/internships` and `/projects` (marketplace browse) → `/internships/[id]` with an Apply flow (confirmation dialog, application tracked in "My Applications")
- `/my-applications` — status pipeline (Applied → Under review → Interview → Offer/Rejected), each stage timestamped
- `/leaderboard` — global + hackathon-specific, filterable
- `/profile` — the shared profile component

### Professional
Similar shape to Student but weighted toward projects/marketplace over daily challenges, and adds a `/portfolio` subpage (structured project showcase, not a freeform text field) since professionals are being evaluated by recruiters more directly.

### Mentor
Dashboard home leads with: hackathons/cohorts they're assigned to mentor, pending mentee questions/office-hours requests, and evaluation queue if they're also judging.
Subpages:
- `/mentees` → list of assigned students/teams → `/mentees/[id]` (their progress, submissions, a private notes field only the mentor sees)
- `/office-hours` → a real scheduling view (available slots the mentor sets, students book, calendar view) — Add here means "Add availability slot," Delete means "Cancel a slot" (with a confirmation that warns if someone already booked it)
- `/judging` → hackathons where they're a judge → scoring rubric per submission (structured fields matching the hackathon's stated judging criteria from module 4, not a single free-text box)
- `/profile` — mentor-specific stats: mentees helped, avg rating from mentees, hackathons judged

### Recruiter
Dashboard home leads with: active job/internship postings and their funnel numbers, new applicants needing review, and saved/shortlisted candidates.
Subpages:
- `/postings` → `/postings/new` (structured job form: role, type, stipend/salary band, skills required, deadline) → `/postings/[id]/applicants` (kanban or table pipeline, drag or dropdown to move stage — moving to "Rejected" triggers a confirmation since it notifies the candidate)
- `/talent-search` → the Talent Marketplace: filterable search over student/professional profiles (skills, hackathon history, badges, availability) — this is Unstop's "Talent Search" equivalent and should feel powerful, not a plain table
- `/candidates/[id]` → full profile view as the recruiter sees it (portfolio, hackathon history, AI evaluation scores if the candidate has opted to share them, notes field private to this recruiter)
- `/shortlist` → saved candidates
- `/profile` — company-linked recruiter profile, postings live, hires made

### Company Admin
Sits above Recruiter: manages the company's presence and multiple recruiter seats.
Subpages:
- `/company-profile` → the public-facing company page (logo, description, tech stack, culture content) with an edit flow
- `/team` → manage recruiter seats on the account (Add recruiter = invite by email with role, Delete = remove seat, confirmation warns their postings get reassigned or archived)
- `/postings` (aggregate view across all recruiters) and `/analytics` (company-level: applicant volume, funnel conversion, cost/time-to-hire style metrics if in scope)

### Platform Admin
Operational control plane, not a public-feeling dashboard — should read more like an admin console (denser tables, fewer illustrations, more mono-font data).
Subpages:
- `/users` → search/filter all users, role management, suspend/reinstate (confirmation dialogs, obviously — these are high-stakes actions)
- `/hackathons/review` → moderation queue for hackathons pending approval before going live
- `/reports` → flagged content/users needing action
- `/platform-analytics` → the real Analytics module: DAU/MAU, streak retention, hackathon participation trends, marketplace activity — charts should be real components (recharts or similar) bound to real aggregation logic, not static images

## 5. AI Evaluation module (ties into Daily Challenges and Judging)

This deserves its own care since it's the most technically distinctive module (Phase 2, in progress):
