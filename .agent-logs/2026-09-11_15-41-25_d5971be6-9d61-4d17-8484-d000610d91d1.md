Here is a full overview of the **Detask** project that we have built:

### 1. Project Purpose
Detask is a production-grade collaborative task management application tailored for a hackathon submission. It focuses heavily on technical depth, a premium user experience, and architectural correctness.

### 2. Core Technologies Used
- **Frontend Framework**: Next.js 14 (App Router) using React Server Components and Client Components where interactivity is needed.
- **Language**: TypeScript (strict mode) for end-to-end type safety.
- **Styling**: Tailwind CSS combined with `shadcn/ui` components for a premium, accessible, and minimalist aesthetic.
- **Database**: SQLite (via Prisma ORM). The schema is explicitly designed so that migrating to PostgreSQL for a production deployment requires changing only one line (`provider = "postgresql"`).
- **Authentication**: NextAuth.js utilizing a secure Credentials provider with `bcrypt` for password hashing and JSON Web Tokens (JWT) for session management.
- **Real-time Synchronization**: Pusher. Chosen over custom WebSockets (Socket.io) to ensure seamless compatibility with serverless deployment environments like Vercel.
- **Interactions**: `@hello-pangea/dnd` handles the drag-and-drop mechanics for the Kanban board.

### 3. Architecture & Security (The Differentiators)
- **Centralized RBAC (Role-Based Access Control)**:
  Instead of scattering conditional checks throughout the UI, access is governed by a strict matrix defined in [`lib/permissions.ts`](file:///C:/Users/ansik/Desktop/Detask/lib/permissions.ts). Three distinct roles exist:
  - **Admin**: Full workspace control.
  - **Manager**: Project creation and task assignment.
  - **Member**: Can only interact with and update assigned tasks.
- **Multi-layer Enforcement**: Permissions are enforced strictly at the Server Action layer (before any database mutations occur) and optionally on the UI layer to hide unauthorized actions.
- **Event-Driven UI**: When a user moves a task, the UI updates optimistically, the server validates and commits the change to Prisma, and Pusher broadcasts an event to sync all other active clients instantly.

### 4. Codebase Structure
The project follows a clean and scalable Next.js directory structure:
- **`src/app/`**: Contains the routing logic. 
  - `page.tsx`: The main protected Dashboard/Kanban view.
  - `login/page.tsx`: The authentication interface.
  - `actions/`: Contains Next.js Server Actions (e.g., `task.ts` for updating tasks securely).
  - `api/auth/[...nextauth]/route.ts`: The NextAuth backend handler.
- **`src/components/`**: 
  - `ui/`: Reusable, unstyled-by-default `shadcn` components (buttons, cards, inputs).
  - `kanban-board.tsx`: The heavy-lifting client component that manages drag-and-drop state and Pusher subscriptions.
  - `auth-provider.tsx`: Wraps the application in NextAuth session context.
- **`src/lib/`**: 
  - `prisma.ts`: Initializes the Prisma singleton to prevent connection exhaustion in development.
  - `auth.ts`: Contains the NextAuth configuration, credentials logic, and token callbacks.
  - `permissions.ts`: The core RBAC matrix and validation functions.
- **`prisma/`**: 
  - `schema.prisma`: The relational database schema defining Users, Workspaces, Projects, Tasks, Comments, and Activity Logs.
  - `seed.ts`: A script to inject initial test data and role-specific accounts.
